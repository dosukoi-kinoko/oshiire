## 1. プロダクト概要とゴール

### 1.1 プロダクト定義

推し活に特化した「推しの情報をひとつにまとめる」PWA（Progressive Web App）。
SNSリンク集・ニュース・カレンダー・記録・グッズ管理を1アプリで完結させる。

### 1.2 オーナーの5大ゴールと本書での担保方法

| # | ゴール | 本書での担保 |
|---|---|---|
| 1 | 可能な限りゼロコスト | §8 で無料枠内に収まる構成に全面見直し（企画書の構成はゼロコストが崩れる箇所あり → §2） |
| 2 | 後々収益が見込める作り | §9 フリーミアム設計。無料版のコスト構造を「ユーザーが増えても費用がほぼ増えない」形に設計 |
| 3 | デザイン性のよさ | §5.4 デザイン要件（3テーマ×3レイアウト、Lighthouse・アニメーション基準を数値定義） |
| 4 | 使い勝手のよさ | §5.3 UX非機能要件（操作ステップ数・応答時間を数値定義）、§4 の各機能に受け入れ基準 |
| 5 | 口コミで使いたくなる仕様 | §12 グロース要件（布教カード・バッジ・「1年前の今日」等をバイラル装置として要件化） |

### 1.3 成功指標（KPI）

| フェーズ | 指標 | 目標値 |
|---|---|---|
| フェーズ1（クローズドβ） | テスター継続利用率（7日） | 50%以上 |
| フェーズ2（一般公開後6ヶ月） | 登録ユーザー数 | 1,000人 |
| フェーズ2 | 有料転換率 | 3%（企画書の5%は楽観値のため下方修正 → §2 穴13） |
| フェーズ2 | 布教カード経由の新規流入比率 | 20%以上 |
| 常時 | 月間ランニングコスト（〜1,000人時点） | フェーズ1: ¥0 / フェーズ2以降: 約¥500/月（バーチャルオフィス）+ドメイン代 約¥1,500/年 |

## 2. 【最重要】企画書レビュー：発見した穴と対応方針

企画書 v1.01 を技術・コスト・法務の観点で検証した結果。**深刻度：🔴致命的（このままだと公開不可/ゼロコスト崩壊）、🟡要修正、🟢軽微**。

### 🔴 穴1: Vercel無料プラン（Hobby）は商用利用禁止

- **問題**: 企画書はホスティングを「Vercel（無料プラン）¥0」とするが、Vercel Hobbyプランは**利用規約で非商用利用に限定**されている。プレミアムプラン（月額¥250）を販売した時点で規約違反となり、アカウント停止リスクがある。Proプランは$20/月（約¥3,000/月）でゼロコスト方針と矛盾。
- **対応**: ホスティングを **Cloudflare Pages（無料枠で商用利用可・帯域無制限）** に変更する。Next.js は Cloudflare 上で動作可能（OpenNext/静的エクスポート）。フェーズ1（無償βの間）はVercel Hobbyでも可だが、**課金開始前に必ずCloudflareへ移行**する。

### 🔴 穴2: Firebase Storage は新規プロジェクトで無料利用不可

- **問題**: 企画書は「Firebase Storage（5GBまで無料）」とするが、**2024年10月以降、新規Firebaseプロジェクトでは Cloud Storage の利用に Blaze プラン（クレジットカード登録必須の従量課金）が必要**になった。「5GB無料」は過去の情報。
- **対応**: BaaS を **Supabase に一本化**（企画書の「Supabase or Firebase」の二択を解消）。Supabase無料枠: DB 500MB / Storage 1GB / 認証 5万MAU。ただしStorage 1GBは写真アプリには少ないため、**写真の保存戦略を根本から見直す（→ 穴4）**。

### 🔴 穴3: 「SNS小窓で一覧表示」はX（Twitter）の仕様変更により当初構想のままでは実現不能

- **問題**: 差別化の核である「X・Instagram・TikTok・YouTubeを小窓で一覧表示」のうち、
  - **X**: タイムライン埋め込み（Timeline Embed）は2023年以降ほぼ機能停止。APIで投稿を取得するには有料プラン（$200/月〜）が必要。無料でできるのは「単一ポストの埋め込み」と「プロフィールへのリンク」のみ。
  - **Instagram**: oEmbed利用にはMeta開発者アプリ登録+審査+アクセストークンが必要。個人開発では審査ハードルが高い。
  - **TikTok / YouTube**: 公式埋め込みが無料で利用可能（YouTubeはチャンネル埋め込み・RSSも可）。
- **対応**: 「SNS小窓」の要件を以下に再定義する（FR-11参照）。
  1. **YouTube**: 最新動画の小窓表示（RSS `https://www.youtube.com/feeds/videos.xml?channel_id=` 利用、無料・規約適合）
  2. **TikTok**: 公式embed
  3. **X / Instagram**: 「公式風デザインのリンクカード」（アイコン+アカウント名+タップで公式アプリ/サイトへ遷移）。新着自動取得は行わない
  4. 将来X APIの料金・仕様が緩和された場合に小窓化できるようアダプタ層を設けておく
- **付随修正**: 「NEWバッジ（SNS新着投稿時にパルス通知）」はSNSポーリングが前提のため**実現不能。要件から削除**し、代替として「推し登録日・記録追加時のNEW演出」に変更。差別化表の「SNS小窓表示 ✅」は正確には「YouTube/TikTok小窓+SNSリンクカード」と表現を改めること（誇大表示は口コミで逆効果）。

### 🔴 穴4: 無料プラン「2GBストレージ」はゼロコストと数学的に両立しない

- **問題**: Supabase無料枠のStorageは**全ユーザー合計で1GB**。無料ユーザー1人に2GB配ると1人目で枯渇する。企画書の収支シミュレーション（1,000人でサーバー費¥3,000）も写真クラウド保存前提では大幅な過小見積り。
- **対応**: ストレージ戦略を以下に確定する。
  - **無料プラン**: 写真は**端末内保存のみ**（IndexedDB/OPFS、PWAで永続化）。クラウドには**テキストデータのみ**同期（1ユーザーあたり数百KB → 無料枠で数千人収容可能）。
  - **プレミアム**: 写真クラウドバックアップ（1ユーザー上限10GB、Cloudflare R2 使用。R2は10GB無料+エグレス無料、超過分は有料ユーザーの収益から支払う従量課金で赤字にならない）。
  - 写真はアップロード前にクライアント側で自動圧縮（長辺1600px / WebP / 目安300KB以下）。
  - この設計により「無料ユーザーが何万人増えてもストレージ費用ほぼゼロ」を実現し、ゴール1と2を両立する。

### 🔴 穴5: 特定商取引法表記に個人の氏名・住所の公開が必要

- **問題**: 企画書は特商法表記の必要性には触れているが、**個人開発者は原則として本名・住所・電話番号をネット上に公開する義務がある**点が漏れている。推し活アプリのユーザー層を考えると開発者の個人情報公開はリスク。
- **対応（オーナー決定済み）**: **バーチャルオフィス方式を採用**。月額¥500〜のレンタル住所を契約して特商法ページに記載し、個人の住所・電話番号は一切公開しない。ゼロコスト方針の唯一の例外的固定費（年間約¥6,000〜）として予算化する。契約は**課金機能公開前（フェーズ2開始時）の必須タスク**。フェーズ1（無償β）の間は不要。

### 🟡 穴6: 「Sign in with Apple」はApple Developer Program（$99/年）が必要

- **問題**: 企画書は認証を「Google / Apple SNSログイン ¥0」とするが、Sign in with AppleはWebでも**Apple Developer Program（約¥15,000/年）への加入が必須**。
- **対応**: フェーズ1〜2は **Googleログイン + メールMagic Link（パスワード不要）** の2方式とする。Appleログインはフェーズ3のiOSアプリ化（どのみちDeveloper Program加入が必要）と同時に追加。

### 🟡 穴7: 「メールアドレス不要」と「トライアル終了3日前にメール送信」が自己矛盾

- **問題**: §8（安心・安全設計）で「メールアドレス不要」、§7（収益）で「トライアル終了3日前にメール自動送信」。メールを持っていないユーザーにメールは送れない。
- **対応**: 無料利用は匿名（メール不要）で可能とし、**課金時（トライアル開始時）のみメール登録必須**とする。トライアル終了通知はメール+アプリ内通知の二重化。メール送信はResend（無料枠3,000通/月）を使用。

### 🟡 穴8: 「メモ・日記はデバイス内保存を基本」と「複数端末同期」が矛盾

- **問題**: 端末内保存が基本ならスマホ・タブレット・PC間で同期できない。2つの要件が両立しない。
- **対応**: データ分類を確定する（§7.3）。
  - テキストデータ（記録・日記・グッズ情報等）: **クラウド同期が基本**（Supabase、通信・保存時暗号化）。オフライン時はローカルキャッシュで閲覧・編集し、オンライン復帰時に同期。
  - 写真: 無料はローカルのみ、プレミアムはクラウド同期（穴4の通り）。
  - 「日記を端末内のみに保持するプライベートモード」はON/OFF可能なオプションとして提供（ONにすると同期対象外である旨を明示）。

### 🟡 穴9: QRコード1枚でのデータ移行は物理的に不可能

- **問題**: QRコードの最大容量は約3KB。写真どころか記録データすら入らない。
- **対応**: QRコードには**一時的な移行トークン（有効期限10分・ワンタイム）を載せる方式**に変更。旧端末で発行 → 新端末で読み取り → クラウド経由でデータ転送。ローカル写真は同一Wi-Fi内転送は実装コストが高いため、**移行時のみ72時間有効の一時クラウド領域を経由**（無料ユーザーも利用可、転送後自動削除）。

### 🟡 穴10: ノーコード（Bubble/Glide）からPWAへの移行は「全部作り直し」

- **問題**: フェーズ1をBubble/Glideで作ってもコードは一切引き継げず、フェーズ2で二重開発になる。Bubbleの実用プランは有料（$29/月〜）でゼロコストにも反する。
- **対応**: **最初からNext.js + Supabaseで構築**する（本リポジトリで開発）。Claude Code等のAIコーディング支援を使えばノーコードと同等の速度で「本物」を作れるため、ノーコード工程を廃止。企画書§11の「エンジニア依頼費用¥50〜150万」も、AI支援開発により大幅に圧縮可能な前提に更新。

### 🟡 穴11: 「Appleスクリーンタイム・Googleファミリーリンクと自動連携」はPWAでは技術的に不可能

- **問題**: これらはネイティブOS機能であり、Web/PWAから連携するAPIは存在しない。
- **対応**: 要件から削除。未成年保護は「登録時の生年月日入力 → 18歳未満は課金時に保護者同意チェック+確認画面」+「外部リンク遷移時の確認画面」で担保（§10.3）。ネイティブアプリ化した際に改めて検討。

### 🟡 穴12: reCAPTCHA の無料枠は大幅縮小済み

- **問題**: Google reCAPTCHAは2025年より無料枠が月10,000評価に縮小され、超過は有料。
- **対応**: **Cloudflare Turnstile（無料・回数無制限）** に変更。

### 🟡 穴13: 収支シミュレーションが楽観的すぎる

- **問題**: 転換率5%はフリーミアムアプリとしては高い（業界水準1〜3%）。またApple Developer費・ドメイン費・メール送信費が費用に含まれていない。
- **対応**: KPIは転換率3%を基準に再計算。1,000人×3%×¥250=月¥7,500。§8の構成なら1,000人時点のサーバー費は¥0のため、**転換率3%でも黒字**が成立する（この「低コスト体質」が本書の技術選定の根拠）。

### 🟡 穴14: 布教カードの肖像権・著作権リスク

- **問題**: 「ユーザーが撮影した写真のみ使用可」としても、**推し本人が写った写真をSNSに公開シェアすると肖像権・パブリシティ権の問題が発生**する（私的利用と公開は別）。布教カードは公開が前提の機能なので矛盾する。
- **対応**: 布教カード生成時に選べる素材を「テキスト+テーマデザイン+絵文字+ユーザーの推し歴データ（記録数・バッジ等）」に限定し、**写真入りカードには「権利上問題ない写真か確認しましたか？」の確認ステップ+ガイドライン表示**を必須とする。デフォルトは写真なしのデザインカード。

### 🟢 穴15: Google News RSSはブラウザから直接取得できない（CORS）

- **対応**: サーバー側（Cloudflare Pages Functions / Supabase Edge Functions、無料枠内）でRSSを取得・キャッシュ（30分）して配信する。RSSソースはGoogle News RSSを主、Yahoo!ニュースRSS等を副として2系統確保（企画書のリスク対策を要件化）。

### 🟢 穴16: 「週1回・毎晩深夜」のクラウド自動バックアップの表現矛盾と実装方式

- **問題**: 「週1回」と「毎晩」が矛盾。またPWAは端末側で夜間バックグラウンド実行できない。
- **対応**: クラウド同期型（§7.3）なら「バックアップ」は常時同期で自動達成される。別途「JSONエクスポート」を手動実行機能として提供。表現を「データは自動的にクラウド同期。加えて手動エクスポート可」に整理。

### 🟢 穴17: 「ワンタップ登録：名前検索→タップ」に必要な推しマスターデータの整備コストが未定義

- **対応**: フェーズ1〜2は**自由入力+ジャンル別テンプレート**（入力補助）とする。マスターデータ（有名人DB）の整備は運用コストが大きく著作権・実在人物データの扱いも絡むため、フェーズ3以降の検討事項とする。「ワンタップ」の使い勝手は入力フォームの最適化（名前+ジャンルの2項目だけで登録完了）で担保。

### 🟢 穴18: 通報機能の対象がフェーズ1〜2に存在しない

- **問題**: フェーズ1〜2はコミュニティ機能なし（数字のみのゆるいつながり）のため、通報すべきUGCの公開面がない。
- **対応**: 通報・アカウント停止・不適切語フィルターは**コミュニティ機能と同じフェーズ3に移動**。ただし布教カード（外部シェア）は公開面になるため、カード内テキストへの不適切語フィルターのみフェーズ2で先行実装。

### v1.2 追加レビューで発見した穴（19〜24）

#### 🔴 穴19: iOS Safariの「7日ルール」で無料ユーザーの写真が全損するリスク

- **問題**: 無料プランの写真は端末内保存のみ（穴4対応）だが、**iOS Safariは7日間利用のないサイトのIndexedDB等を自動削除する**（ITP仕様）。ホーム画面追加（PWAインストール）済みなら対象外だが、**ブラウザのまま使い続けて7日間開かないと写真・未同期データが全て消える**。推し活が忙しくない時期に1週間空くのは普通にあり得るため、「大事な思い出が消えた」は口コミ最悪シナリオ。
- **対応**:
  1. iOS Safari利用時はオンボーディングで**ホーム画面追加を強く誘導**（追加するとデータが守られる旨を明示。手順アニメ付き）
  2. 未追加のままのユーザーには写真保存時に「7日間開かないと消える可能性」を警告バナー表示
  3. `navigator.storage.persist()` を必ず要求し、結果を設定画面で可視化（NFR-13の強化）
  4. プレミアム訴求ポイントにもなる（「クラウドバックアップなら消えません」）— 恐怖訴求にならない文言に注意

#### 🟡 穴20: 企画書の「名刺モード」（アーティスト側の活用）が要件から漏れていた

- **問題**: 企画書§2「自分のページを名刺代わりに使える（名刺モード）」を本書v1.0が取りこぼしていた。ただし公開URLページはUGCの公開面となり、通報・権利・スパム対策（穴18で先送りした一式）が必要になる。
- **対応**: **フェーズ3スコープに正式に位置づける**（コミュニティ機能と同じ回で実装）。フェーズ2までは布教カード（画像）が名刺の代替となる旨を明記。

#### 🟡 穴21: 「ホーム画面ウィジェット」の扱いが未定義だった

- **問題**: 企画書の拡張機能📱を本書がどのフェーズにも割り当てていなかった。かつ**PWAではiOSウィジェット提供は不可能**（Androidも実質不可）。
- **対応**: フェーズ3（ネイティブアプリ化）の目玉機能として明記し、§4.6の変更表に追加。

#### 🟡 穴22: 「同じ推しを◯人が推しています」は表記ゆれで成立しない

- **問題**: 推し名は自由入力（穴17）のため、「尊富士」「たける富士」「Takerufuji」が別人扱いになり、GR-04のカウントが実態より小さく出て逆に寂しい。
- **対応**: GR-04の成立条件を「名前の正規化（空白・記号除去、カナ統一）+ジャンル一致」で近似マッチとし、**一定数（10人）未満の場合はカウント自体を表示しない**（「1人が推しています」は寂しさの演出になるため）。

#### 🟡 穴23: 推しの誕生日・記念日の要件が欠けていた

- **問題**: 推し活の最重要イベントである**推しの誕生日・デビュー日・周年**が、汎用カレンダー機能（FR-16）に埋もれていて専用要件がなかった。毎年自動で繰り返す・お祝い演出・「推し始めて◯◯日」の節目通知は手動イベント登録では実現できない。
- **対応**: FR-16aとして新設（§4.3）。

#### 🟢 穴24: Magic Linkログインのメール収集がプライバシーポリシー記載と不整合
